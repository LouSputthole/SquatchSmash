# Engine traps

Bugs this codebase has produced more than once, each written down after it was
found the hard way. Every entry is a real defect with a real fix in the history,
not a hypothetical. Read this before writing audio mixing, a browser check, or a
scene's dialogue wiring.

Related: `TONE-AND-PARODY.md` governs what the game says. This is about the
machinery underneath it lying to you.

---

## 1. Overlapping AudioParam ramps stack; they do not replace

**Symptom.** Rain playing at full outdoor volume inside a closed nightclub,
after the code had explicitly ducked it to 0.018.

**Mechanism.** A Web Audio `AudioParam` keeps *one* automation timeline, sorted
by time. `linearRampToValueAtTime` does not cancel what is already on it. So a
short ramp scheduled while a longer one is still running is inserted **before**
it: the parameter reaches your new value exactly on schedule, and then keeps
travelling to the older target and stays there.

`startLoop` fades in over 1.2 s and `startMusicLoop` over 1.4–2 s. Every scene's
first room resolution happens on frame one, *inside* that window. So the room
mix landed and was then overwritten by the fade-in it had interrupted — in the
HotDog party, three loops at once, one of them 17× too loud.

**The rule.** Never ramp a param without anchoring it first. `AudioEngine._rampParam`
does this and `setLoopVolume` / `setLoopCutoff` / `stopLoop` all go through it:

```js
if (param.cancelAndHoldAtTime) param.cancelAndHoldAtTime(t);
else { param.cancelScheduledValues(t); param.setValueAtTime(param.value, t); }
param.linearRampToValueAtTime(value, t + ramp);
```

**Why it survived so long.** The test stub for `AudioParam` collapsed every ramp
to its target the instant it was scheduled, so no test could express the failure.
`tests/audio-engine.test.mjs` now has `timelineParam`, which keeps a real sorted
timeline and can be sampled at a time. If you are testing anything about fades,
use that one.

## 2. The simulation clock is not the wall clock

**Symptom.** Browser checks that pass on an idle box and time out on a loaded
one, at a different place each time.

**Mechanism.** Every scene clamps its step (`Math.min(0.05, …)`) so a stalled tab
cannot teleport the player through a wall. Under swiftshader with several
verifiers running, a page renders at a few frames a second — so one second of
wall clock buys a small fraction of a second of *simulated* time. Anything
measured in simulated seconds takes far longer than its nominal duration.

Three real instances:

- `await page.waitForTimeout(1650)` before releasing a 1.05 s hold. The hold had
  earned nothing; the check had measured the rasteriser.
- A 10 000 ms budget for a 2.3 s body-placement tween.
- `page.click`, whose visible/stable/hit-testable wait is served by the page's
  own main thread — the thread that is busy building the scene.

**The rule.** Never sleep for a duration and assume progress. Wait on a
predicate the game itself publishes, and give it a budget that is generous
rather than tight — a large timeout costs nothing when the condition is met, and
only changes how long a genuine failure takes to report. Where no predicate
exists, add one: `GRAVEYARD.disrespectEarned` exists precisely because
`stopPee()` judges two conditions and nothing outside could see either.

`tools/verify-bing-two.mjs` has the shape to copy: one named `SIM_WAIT`, plus
`page.setDefaultTimeout(SIM_WAIT)` so implicit waits get it too.

## 3. A scene with no VO generator is invisible, however much is written for it

**Symptom.** Fully authored, fully wired dialogue that nobody knows is
unrecorded, playing silent-with-subtitles forever.

**Mechanism.** `VOICE-LINES-TODO.md` — the sheet the owner records from — is
built from `assets/sfx/manifest.json`. The manifest is generated by the
`tools/<scene>-vo.mjs` family, joined by `npm run vo:sync`. A scene without one
of those tools contributes nothing to the manifest, so its lines never reach the
sheet, so nobody learns they are missing.

This has happened three times: 147 lines across The Silver Case and The Enola
Squatch, and 55 in THE TAKE — including eleven of Big Uncle Lou's fourteen and
every word a bank hostage says.

**The rule.** Writing dialogue is half the job. A new scene needs a generator in
the same change, registered in `vo:sync`, with a `collect*` / `sync*` / `check*`
trio and a test asserting the committed manifest matches the script.

**Corollary — manifest is truth, `hasSample()` is not.** A cue in the manifest
with no file on disk is a delivered *cue*, not a delivered *recording*.
`assets/sfx/index.json` lists what actually exists, and the loader consults it,
so an unrecorded cue costs nothing at runtime.

## 4. Do not rebuild a manifest block by prefix without checking who else owns it

`heist.` names both THE TAKE's 112 dialogue lines **and** its 46 sound effects
(`heist.bank.alarm`, `heist.map.paper`). Every other scene's generator filters by
prefix; `tools/heist-vo.mjs` cannot, and owns exactly the ids its script
declares. A prefix rebuild there would silently delete the scene's whole effects
bank. There is a test for it.

## 5. Gates that lie

The recurring shape behind most of the playtest list: a check that reports
success without exercising what the player does.

- A check that **teleports past the blocker** it is meant to prove — the Front
  and Center stairs passed for weeks because nothing ever walked down them. The
  ramps arrived nowhere; there was no undercroft to arrive in.
- A check that asks a **different question than the one that matters** — "did he
  get down" rather than "did he arrive".
- A check that **accepts a fallback as success**, so the fallback becomes the
  shipped behaviour and nobody notices the real path is dead.
- A check pinning **the exact thing being complained about** — `verify:bing-two`
  asserted `wrapGeometry === 'CapsuleGeometry'` and `/service-exit arrows/`, both
  of which were the defect. Fix the behaviour and move the assertion to the new
  correct one; never revert the behaviour to satisfy the check.

**The rule.** Walk it. If the player walks somewhere, the check walks there. If
the player holds a button, the check holds the button and waits for what the
button earns.
